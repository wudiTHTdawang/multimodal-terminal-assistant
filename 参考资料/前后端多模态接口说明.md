# 前后端多模态接口说明

> 本文是前端与后端共同遵守的接口约定。任何一方修改字段名、字段含义或时间窗口前，都应先更新本文并通知对方。

## 1. 这份约定解决什么问题

系统需要把三类输入放在同一时间轴上理解：

- 用户通过摄像头产生的注视结果；
- 用户当前看到的页面和页面对象；
- 用户提交的模拟语音文本。

摄像头画面不会传给后端。前端只把已经处理好的结构化结果发给本机后端，例如“用户稳定注视张三 1.2 秒”。

```text
摄像头本地关键点与视线估计 ──→ gaze 事件 ──┐
当前页面及可见对象 ───────────→ screen_context ─┼→ 本机后端短时事件缓存
模拟语音文本 ─────────────────→ speech_text ───┤             ↓
明确询问后的头部动作 ─────────→ head_gesture ──┘
                                                        时间对齐与意图理解
                                                               ↓
                                                    确认框、澄清问题或模拟执行
```

## 2. 谁负责什么

| 角色 | 负责内容 |
| --- | --- |
| 前端 | 发现模态事件、构建 JSON、先做基础校验、通过 HTTP 发送、展示理解结果 |
| 后端 | 再次校验 JSON、短时缓存事件、按时间窗口合并事件、识别意图、返回解释与执行结果 |
| 共同确认 | 字段名称、字段含义、时间单位、阈值、支持的意图、错误提示 |

## 3. 所有请求的统一外层格式

浏览器所有业务请求都发送到：

```text
POST http://127.0.0.1:8000/api/action
Content-Type: application/json
```

请求最外层使用统一格式：

```json
{
  "action": "操作名称",
  "其他字段": "该操作需要的数据"
}
```

`action` 不是模态本身，而是告诉后端“这一次请求要做什么”。常用值如下：

| `action` | 含义 |
| --- | --- |
| `record_multimodal_event` | 记录一条结构化模态事件到短时缓存 |
| `understand_multimodal_command` | 合并近期语音、视线和页面上下文，理解用户意图 |
| `select_contact` | 选择联系人；可作为摄像头不可用时的备用输入 |
| `confirm_send` / `cancel_message` | 确认或取消待发送消息 |
| `query_schedule` | 读取本地授权备忘录中的日程 |
| `start_mode` | 启动一个模式并检索该模式的首个推荐歌曲 |
| `like_track` / `complete_track` | 提高歌曲偏好值并加入当前模式偏好歌单 |
| `next_track` | 降低当前歌曲偏好值并检索下一首推荐歌曲 |
| `advance_track` | 当前歌曲已完成用户反馈后，不降低偏好地继续推荐下一首 |

音乐推荐不依赖第三方音乐平台登录或真实用户歌单。系统使用本地模拟曲库、分模式歌曲偏好歌单和项目内置的“平台大众常听”列表生成推荐；后者仅用于演示冷启动与探索推荐，不代表真实平台统计。

## 4. 共同字段字典

每一条模态事件都使用下面的结构：

```json
{
  "modality": "gaze",
  "timestamp_ms": 1760000000000,
  "confidence": 0.84,
  "payload": {}
}
```

| 字段 | 类型 | 含义与规则 |
| --- | --- | --- |
| `modality` | 字符串 | 输入来源，只能是 `gaze`、`screen_context`、`speech_text`、`head_gesture` |
| `timestamp_ms` | 整数 | 浏览器使用 `Date.now()` 产生的毫秒时间戳；所有事件必须使用同一单位 |
| `confidence` | 数字 | 前端估计的可信度，取值范围必须是 `0~1` |
| `payload` | 对象 | 该模态特有的数据；不能直接上传视频帧、截图或原始人脸关键点 |

## 5. 四种当前支持的事件

### 5.1 `gaze`：稳定注视结果

触发条件：完成 9 点校准后，用户对当前页面某一对象稳定注视至少约 `1200ms`。

```json
{
  "action": "record_multimodal_event",
  "event": {
    "modality": "gaze",
    "timestamp_ms": 1760000000000,
    "confidence": 0.84,
    "payload": {
      "page": "message",
      "target_type": "contact",
      "target_id": "contact_zhangsan",
      "zone": "middle-left",
      "dwell_ms": 1250,
      "calibration": "9-point-multi-frame-v2"
    }
  }
}
```

| `payload` 字段 | 含义 |
| --- | --- |
| `page` | 产生注视时所在模块：`message`、`music` 或 `memo` |
| `target_type` | 对象类型：`contact`、`music_track` 或 `schedule_item` |
| `target_id` | 对象的稳定 ID，例如 `contact_zhangsan`；后端据此查找联系人 |
| `zone` | 注视所在粗区域，例如 `middle-left`；用于调试和解释，不单独决定执行结果 |
| `dwell_ms` | 稳定停留时间，单位毫秒 |
| `calibration` | 所使用的校准版本，便于比较不同算法效果 |

### 5.2 `screen_context`：屏幕上下文

触发条件：页面初始化、切换模块、日程列表重新渲染后。

```json
{
  "action": "record_multimodal_event",
  "event": {
    "modality": "screen_context",
    "timestamp_ms": 1760000000100,
    "confidence": 1,
    "payload": {
      "page": "message",
      "visible_targets": [
        {
          "target_type": "contact",
          "target_id": "contact_zhangsan",
          "label": "张三",
          "zone": "middle-left"
        }
      ]
    }
  }
}
```

`screen_context` 的作用是防止后端只根据一个 ID 做猜测。后端会检查：用户注视的联系人是否仍在当前联系人页面中。

### 5.3 `speech_text`：模拟语音文本

触发条件：用户点击“提交模拟语音指令”。未来接入真实语音识别后，识别完成的文本沿用此格式。

```json
{
  "action": "record_multimodal_event",
  "event": {
    "modality": "speech_text",
    "timestamp_ms": 1760000001200,
    "confidence": 1,
    "payload": {
      "text": "给他发消息，晚点开会",
      "page": "message",
      "source": "simulated"
    }
  }
}
```

### 5.4 `head_gesture`：明确询问后的头部确认

触发条件：系统已针对联系人选择或消息发送显示明确的是 / 否问题，或用户已稳定注视音乐页的当前歌曲卡片，且本机摄像头检测到明显的纵向或横向头部运动。纵向运动近似表示点头（确认/喜欢），横向运动近似表示摇头（拒绝/不喜欢）。该事件不上传视频帧或人脸关键点，仅保留最终动作结果。

```json
{
  "action": "record_multimodal_event",
  "event": {
    "modality": "head_gesture",
    "timestamp_ms": 1760000001500,
    "confidence": 0.72,
    "payload": {
      "page": "message",
      "decision": "confirm",
      "gesture": "nod",
      "purpose": "message_confirmation"
    }
  }
}
```

| `payload` 字段 | 含义 |
| --- | --- |
| `page` | `message` 或 `music`；音乐页只在稳定注视当前歌曲卡片后启用 |
| `decision` | `confirm` 或 `reject`，供本轮确认动作使用 |
| `gesture` | `nod` 或 `shake`，用于演示记录和调试 |
| `purpose` | `contact_selection`、`message_confirmation` 或 `music_feedback`，说明这次动作回答的问题 |

## 6. 浏览器端的关键流程

前端的统一发送函数在 `web/app.js`：

```js
async function api(action, extra = {}) {
  return fetch('/api/action', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ action, ...extra }),
  });
}
```

真正上报模态事件前，前端先检查模态名称、毫秒时间戳、置信度范围和 `payload` 是否存在。然后调用：

```js
await api('record_multimodal_event', { event });
```

提交模拟语音时，前端顺序是：

```text
构建 speech_text 事件
→ record_multimodal_event
→ understand_multimodal_command（携带本条语音的 timestamp_ms）
→ 根据后端结果展示确认框或澄清提示
```

## 7. 后端如何接收与保护数据

后端入口位于 `app.py` 的 `do_POST()`：

```python
length = int(self.headers.get("Content-Length", "0"))
payload = json.loads(self.rfile.read(length).decode("utf-8"))
result = self.handle_action(payload)
```

后端依据 `action` 路由：

```python
if action == "record_multimodal_event":
    return record_multimodal_event(payload.get("event"))
```

`record_multimodal_event()` 会再次校验字段。对 `gaze` 事件，至少要求包含：

```python
required = {"page", "target_type", "target_id", "zone", "dwell_ms"}
```

事件只进入 `MULTIMODAL_EVENT_BUFFER` 内存列表：

- 最多保留 100 条；
- 服务器收到超过 10 秒的事件会自动删除；
- 不写入 `runtime_state.json`；
- 不保存摄像头图像、视频、原始关键点或音频。

## 8. 时间对齐与“他”的解析

当后端收到：

```json
{
  "action": "understand_multimodal_command",
  "speech_timestamp_ms": 1760000001200
}
```

对于联系人消息，后端执行以下顺序：

1. 找到该时间戳附近的 `speech_text`；
2. 在语音前 3 秒到语音后 1 秒内筛选 `gaze`（`GAZE_ALIGNMENT_BEFORE_MS=3000`，与 `tests/scenarios.json` 验收口径一致）；
3. 选择置信度和停留时间较高的联系人注视事件；
4. 查找语音前后 5 秒内的 `screen_context`；
5. 检查注视联系人是否出现在该页面的 `visible_targets` 中；
6. 只有三者一致时，才把“他”解析为该联系人；
7. 返回 `intent`、`pending` 和 `explanation`，由前端展示确认框。

对于音乐页，用户选择模式后由本地推荐器直接给出单曲卡片。用户对该卡片稳定注视后，前端仅在此时将点头 / 摇头解释为喜欢 / 不喜欢：喜欢或完整收听将歌曲写入当前模式的偏好歌单；不喜欢则降低这首歌的偏好值并请求下一首推荐。完整收听由本地演示播放进度结束自动触发；后续接入真实音频时应改接播放器结束事件。推荐器优先使用模式偏好歌单，并每三次至少插入一首该模式下的本地“大众常听”歌曲。

示例：

```text
12:00:00.000  gaze：稳定注视张三 1250ms，置信度 0.84
12:00:00.100  screen_context：联系人页可见张三
12:00:01.200  speech_text：给他发消息，晚点开会
                 ↓
intent = send_message
recipient = 张三
content = 晚点开会
```

## 9. 后端返回格式与前端处理

成功响应的外层格式：

```json
{
  "ok": true,
  "result": {
    "message": "将通过常用消息应用向张三发送：‘晚点开会’，是否确认？",
    "intent": "send_message",
    "pending": { "contact": "张三", "content": "晚点开会" },
    "explanation": ["...", "..."]
  }
}
```

前端依据字段显示不同结果：

| 返回字段 | 前端动作 |
| --- | --- |
| `pending` 存在 | 显示“确认发送 / 取消”按钮 |
| `needs_clarification = true` | 显示澄清提示，不执行发送 |
| `clear_message_form = true` | 清空输入框、确认框和联系人高亮 |
| `explanation` | 显示本次判断使用了哪些模态信息 |

失败响应统一为：

```json
{ "ok": false, "error": "本地处理失败：具体原因" }
```

## 10. 修改接口前的检查清单

修改任何共同字段前，两位成员都要确认以下问题：

1. 字段名是否改变？前端构建处、后端校验处、本文档是否同时修改？
2. 时间单位是否仍是毫秒？是否仍使用浏览器 `Date.now()`？
3. 新字段是否涉及隐私？是否会包含原始图像、音频或个人文件内容？
4. 后端在缺失字段、过期事件和低置信度时会返回什么？
5. 是否补充了一个成功案例和一个失败案例用于联调？

## 11. 当前边界与下一步

当前已实现：结构化事件上报、前后端双重校验、10 秒短时缓存、模拟语音与联系人注视的时间对齐、可解释消息确认，以及明确询问后的点头 / 摇头确认和按模式更新的本地歌曲偏好推荐（本机头部运动近似识别）。

当前未实现：真实语音识别、日程的语音意图、模型文件完全离线打包。

后续新增模态时，应优先复用本协议中的 `modality + timestamp_ms + confidence + payload` 结构，再扩展各自的 `payload` 字段。
