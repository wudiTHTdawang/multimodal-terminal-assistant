# 多模态个性化终端助手

> 基于语音、视线与屏幕上下文的端侧智能交互系统

## 1. 项目简介

本项目面向普通 Windows 笔记本电脑，构建一个可在本地运行的多模态个性化终端助手。系统综合用户的语音、视线落点和当前屏幕上下文，理解用户意图、识别操作对象，并生成符合用户偏好的自然反馈。

项目重点解决三类问题：

- 当用户只说“给他发消息”时，系统如何结合用户正在注视的联系人，确定“他”是谁；
- 当用户明确选择专注、开车或娱乐模式后，系统如何基于其播放、喜欢和跳过行为，形成分场景、可解释的本地音乐偏好；
- 当用户授权本地备忘录文件后，系统如何从中整理次日事项、发现时间压力，并提出相应安排建议。

原始音频、视频和已授权备忘录内容均在本地处理，不上传至服务器。若后续使用大语言模型，其职责仅限于将已识别的结构化结果组织为自然语言，不接收原始音视频。

## 2. 首版功能范围

### 2.1 已实现/计划实现

- 设备：普通 Windows 笔记本电脑、摄像头和麦克风；
- 输入：语音、视线、模拟屏幕上下文；
- 视觉反馈：在系统明确提出“是否确认”后支持点头确认；对稳定注视的当前歌曲卡片，点头/摇头分别表示喜欢/不喜欢；
- 页面：模拟联系人、音乐模式和本地备忘录页面；
- 本地消息模拟：确认后在本项目的模拟消息应用中展示发送成功，并清除本轮联系人与正文；
- 数据：本地用户画像、音乐偏好、已授权备忘录索引；
- 隐私：只读取用户主动授权的文件，支持查看和撤销授权。

### 2.2 暂不纳入首版

- 未在当前场景中定义的开放式手势识别；
- 未经用户最终确认的第三方社交平台自动发送；
- 对第三方社交平台的登录、读取、窗口坐标或自动点击；
- 任意第三方音乐平台的登录、歌单读取或播放控制；
- 直接访问 Windows 系统备忘录或第三方备忘录应用数据库；
- 未经确认地修改原始备忘录或创建外部提醒。

## 3. 系统流程

```text
摄像头 / 麦克风 / 当前页面
            │
            ▼
本地感知：语音转写、视线落点、页面对象状态
            │
            ▼
信息同步与综合判断：关联同一轮交互中的语音、视线和页面信息
            │
            ▼
意图与对象识别：动作、对象、内容、置信度、是否需要确认
            │
            ▼
本地偏好与已授权备忘录检索
            │
            ▼
页面反馈 / 文本应答 / 本地操作记录
            │
            ▼
本地模拟消息发送结果
```

### 3.1 信息同步与综合判断

每个输入事件都带有时间戳。系统以一次语音指令为中心，匹配其前后时间窗口内的视线信息和页面状态。例如，用户在联系人页面注视“张三”后说“给他发消息”，系统将“他”与张三的页面对象关联。

系统采用保守策略：

- 明确说出的联系人姓名优先于视线结果；
- 明确否定词（如“不”“别”“取消”）优先于点头等视觉确认；
- 视觉置信度不足或语音、视觉结果冲突时，系统追问确认，不直接执行；
- 点头只在系统提出明确的是/否问题后才代表确认；音乐页还要求先稳定注视当前歌曲卡片，才会把点头/摇头视作喜欢/不喜欢。

## 4. 演示场景

### 场景 A：注视联系人并发送消息

1. 用户打开联系人页面。
2. 用户注视“张三”的卡片。
3. 用户说：“给他发消息，晚点开会。”
4. 系统显示：“将通过常用消息应用向张三发送：‘晚点开会’，是否确认？”
5. 用户点头，或说“确认”“是的”“发送”。
6. 系统在本地模拟消息应用中展示“已向张三发送：晚点开会”，并清空本轮联系人、正文与确认框。

比赛演示不依赖第三方聊天软件，也不会读取聊天记录、写入剪贴板或执行窗口自动化。这样可以将评测重点稳定地放在多模态理解、对象消歧、确认和隐私保护上。

**系统输出**

```json
{
  "intent": "send_message",
  "contact": "张三",
  "content": "晚点开会",
  "requires_confirmation": true
}
```

### 场景 B：多模式下的个性化音乐

系统不凭空判断用户所处场景，而是由用户明确选择专注、开车或娱乐模式。每个模式单独累计音乐偏好，避免将学习时的偏好错误用于开车或娱乐。

1. 用户点击专注、开车或娱乐模式。
2. 系统在本地模拟音乐平台中检索一首适合该模式的歌曲；推荐会优先参考该模式的个人偏好歌单，并每三次至少穿插一次该模式下的“平台大众常听”歌曲。
3. 系统展示单张“正在播放”歌曲卡片及推荐依据，不再要求用户先从多种曲风中选择。
4. 用户点击“我喜欢这首”，系统将歌曲加入当前模式的偏好歌单并提高该歌曲的偏好值。
5. 系统在本地演示播放进度结束时自动判定为完整收听，将当前歌曲加入当前模式的偏好歌单并提高该歌曲的偏好值，然后继续推荐下一首。
6. 用户点击“不喜欢/下一首”，系统降低该歌曲在当前模式下的偏好值，并检索下一首推荐歌曲。
7. 用户注视当前歌曲卡片后，点头等同于“喜欢”，摇头等同于“不喜欢并换下一首”；这一动作只在稳定注视歌曲卡片后才生效。
8. 用户可停止当前模式，或在选择另一个模式时确认切换。播放器和偏好歌单摘要持续显示，不因记录反馈而消失。

首次进入某个模式而没有偏好时，系统使用该模式的本地“大众常听”演示列表作为冷启动推荐；该列表是项目内置模拟数据，不代表真实音乐平台统计。

当前曲库没有真实音频文件，因此“播放结束”由页面显示的本地演示播放进度模拟；后续接入实际音频时，应改由播放器的播放结束事件触发完整收听反馈。

### 场景 C：已授权本地备忘录的日程安排

1. 用户在系统中可一次选择并授权多个备忘录文件；重新选择的文件集会替换此前的授权列表。
2. 系统显示已授权来源及其可撤销选项，并在本地建立索引。
3. 用户查看全部日程安排。
4. 系统汇总所有已授权文件中的事项，按日期和时间排序；已过时间的事项以灰色样式显示。
5. 用户可勾选每项日程的完成状态；完成状态仅保存在本项目本地，不改写原始备忘录。

示例回答：

> 明天有三项安排：10 点组会、14 点提交实验报告、19 点健身。组会结束到报告截止仅有 3 小时，建议你今晚先完成报告初稿。需要我在 9 点 10 分提醒你参加组会吗？

用户说“不要提醒”时，只取消当前提醒。只有用户明确说“以后同类事项都不要提醒”，或连续出现同类行为且系统再次确认后，才更新长期偏好。

## 5. 数据与权限

### 5.1 备忘录文件

首版支持以下用户明确授权的文件格式：

- `.txt`
- `.md`
- `.json`

系统只处理用户主动选择的文件或目录；不扫描其他目录，不读取系统备忘录数据库，不上传备忘录内容。用户可在设置页查看已授权文件，并随时撤销授权和清除本地索引。

推荐的 JSON 备忘录结构：

```json
[
  {
    "id": "memo_001",
    "date": "2026-08-22",
    "time": "10:00",
    "title": "组会",
    "content": "汇报多模态助手项目进展",
    "priority": "high"
  }
]
```

### 5.2 用户画像

用户画像只保存在本地，用于解释系统为何给出某个答案或推荐。初版字段如下：

```json
{
  "preferred_message_app": "模拟消息应用",
  "frequent_contacts": ["张三", "妈妈"],
  "music_preferences": {
    "focus": { "lofi": 2, "light_music": 1, "pure_music": 0 },
    "driving": { "rock": 2, "electronic": 1 },
    "entertainment": { "pop": 2, "jazz": 1 }
  },
  "schedule_reminder_minutes": 50,
  "response_style": "简洁"
}
```

## 6. 性能与验收指标

| 指标 | 首版目标 |
| --- | ---: |
| 三类核心意图准确率 | ≥ 85% |
| 消息场景对象消歧准确率 | ≥ 80% |
| 冲突样本的安全处理准确率 | ≥ 90% |
| 个性化偏好命中率 | ≥ 80% |
| 端到端 P95 延迟 | < 5 秒 |
| 优化目标：端到端 P95 延迟 | < 3 秒 |
| 原始音视频上传次数 | 0 |

端到端延迟从用户说完一句话开始计时，到系统展示理解结果、确认问题或应答为止。P95 表示至少 95% 的测试请求在该时长内完成。

页面的“查看本轮本地多模态处理记录”会实时显示本页面已完成接口的 P50/P95 延迟。该统计用于记录端侧服务处理与页面回传，不把用户的注视等待、说话时长或人工确认时间计入模型响应延迟。

## 7. 低延迟设计

- 本地轻量视觉处理只输出视线落点和头部确认状态；
- 以语音事件为中心缓存短时间的视觉记录，避免重复处理全部视频；
- 页面对象在加载时记录 ID 和坐标，不实时识别整张屏幕；
- 优先采用模板化应答；如调用语言模型，只发送结构化结果并限制输出长度；
- 启动时预热模型，减少第一次交互的等待时间。
- 消息发送在本地模拟应用中完成，不依赖外部软件、账户或网络。

## 本地启动（当前原型）

当前原型不依赖第三方 Python 包。在 PowerShell 中进入项目目录后运行：

```powershell
python app.py
```

随后在浏览器打开 `http://127.0.0.1:8000`。第一版页面以按钮模拟语音、视线与点头输入，用于先验证交互流程和数据读写；后续再将对应按钮替换为真实的语音识别、视线估计和头部点头模块。

人脸模型、手势模型、主脚本与 MediaPipe WASM 运行时均随项目保存在 `web/models/` 和 `web/vendor/`。首次开启摄像头不依赖 Google Storage、jsDelivr 或 unpkg；断网状态下仍可进行本地视线和手势推理。

### 本地模拟消息发送

联系人与正文均在本项目本地完成确认和模拟发送。确认后，系统仅更新本地交互状态并展示发送成功，不会启动第三方聊天软件、读取外部数据、写入剪贴板或执行桌面自动化。这一边界使演示可在无网络、无账号的普通 Windows 笔记本上稳定复现。

若 8000 端口已被旧服务占用，可临时使用其他端口，例如：

```powershell
python app.py --port 8001
```

## 10. 安全原则

- 所有可能影响用户数据或外部系统的动作，都必须得到明确确认；
- 不因单次行为直接改变长期偏好；
- 不将原始音视频、备忘录文本上传到云端；
- 不在未授权范围内读取用户文件；
- 不读取第三方聊天记录，不使用非官方接口、剪贴板写入或屏幕自动点击发送消息；
- 用户可删除本地画像、偏好和备忘录索引。
