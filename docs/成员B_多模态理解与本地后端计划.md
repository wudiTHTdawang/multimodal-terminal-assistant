# 成员 B 计划：多模态对齐、意图理解与本地个性化

## 你的目标

负责让系统“理解”成员 A 采集到的语音、摄像头注视结果和当前屏幕信息。你的阶段性成果是：系统能在本机把“注视张三 + 给他发消息，晚点开会”解析为一条可解释、可确认的消息发送任务。

第一版不要急于训练复杂模型。先做透明、可测试的规则基线；它既能满足演示，也能为后续轻量模型提供对照结果。

## 开始前准备（第 0 天，约 1 小时）

1. 在 VS Code 打开项目并启动本地服务。
2. 阅读：
   - `app.py`：API、状态和当前业务逻辑；
   - `data/contacts.json`：联系人数据；
   - `data/profiles_demo.json`：用户画像；
   - `tests/scenarios.json`：现有场景；
   - `docs/成员A_前端与摄像头视线计划.md`：必须对接的事件格式。
3. 新建分支，例如：`feature/multimodal-fusion`。
4. 约定：数据仅写到本机 `data/runtime_state.json`，该文件不能提交到 GitHub。

## 第 1 阶段：定义统一事件与时间窗口（第 1 天）

### 要做什么

在 `app.py` 中实现 `record_multimodal_event` 操作，将成员 A 发来的事件写入内存或本地运行状态。

每条事件统一有以下字段：

```json
{
  "modality": "gaze | speech_text | screen_context",
  "timestamp_ms": 1720000000000,
  "confidence": 0.0,
  "payload": {}
}
```

### 实现规则

1. 接收后验证字段存在、时间戳是毫秒整数、置信度在 0～1。
2. 只保留最近 10 秒的事件，旧事件自动删除。
3. 不记录摄像头画面、人脸图片、完整关键点轨迹，只记录最终注视目标 ID 和置信度。
4. 增加一个调试接口或页面区域，显示最近事件，方便联调；演示模式下可隐藏。

### 完成标准

- 浏览器发送一个 gaze 事件后，可在后端日志/调试区域看到；
- 11 秒后它会自动失效；
- 非法 JSON 不会让服务崩溃，而是返回清晰错误信息。

## 第 2 阶段：实现“时间对齐 + 信息合并”（第 2 天）

### 用通俗的名称

在代码和文档中将“证据融合”称为 **多模态信息合并**。它的含义是：把同一段时间内的语音、注视和页面信息放在一起判断，而不是分别猜测。

### 第一版规则

当收到一条 `speech_text` 事件时：

1. 取它前后 3 秒内的 gaze 事件；
2. 取它前后 5 秒内的 screen_context 事件；
3. 找到置信度最高、且停留时间至少 800ms 的联系人注视事件；
4. 如果该联系人仍在当前联系人页面中，则把它作为“他”的候选对象；
5. 将最终使用的事件 ID、时间差和置信度写入解释结果。

不要使用“最近一次点击”覆盖摄像头注视结果；点击只作为摄像头不可用时的备用输入，且结果中必须标注来源。

### 输出示例

```json
{
  "intent": "send_message",
  "slots": {
    "recipient_id": "contact_zhangsan",
    "message": "晚点开会"
  },
  "confidence": 0.88,
  "explanation": [
    "检测到语音指令：给他发消息，晚点开会",
    "语音前 1.2 秒持续注视张三卡片 820ms",
    "当前屏幕为联系人页面，因此将“他”解析为张三"
  ]
}
```

## 第 3 阶段：意图与槽位识别（第 3 天）

### 第一版需要支持的意图

| 意图 | 触发示例 | 必填信息 |
| --- | --- | --- |
| `send_message` | 给他发消息，晚点开会 | 收件人、消息内容 |
| `confirm` | 确认、是的、发送 | 当前待确认任务 |
| `cancel` | 取消、不要发送 | 当前待确认任务 |
| `start_music_mode` | 开始专注模式 | 音乐模式 |
| `query_schedule` | 查看我的日程 | 无 |

### 实现建议

1. 先用关键词和简单正则表达式实现；例如语句中同时有“发消息/发送”和消息正文，则识别 `send_message`。
2. 对“给他发消息，晚点开会”分两段：动作词前是命令，逗号后为消息正文。
3. 如果没有候选联系人，返回“请注视或点击需要联系的联系人”，绝不能猜测联系人。
4. 对确认/取消只作用于当前待确认任务；没有任务时提示“当前没有待确认的操作”。

### 完成标准

- 同一条输入重复调用，结果一致；
- 缺失收件人时不发送；
- 所有自动化动作均有确认步骤；
- 错误提示为用户能理解的中文。

## 第 4 阶段：接入当前消息发送模块（第 4 天）

### 要做什么

1. 新增或扩展 `/api/action` 中的 `understand_multimodal_command` 操作。
2. 输入为当前语音事件，服务端自行从事件窗口找 gaze 和 screen_context；不要要求前端自己提前合并。
3. 输出意图、槽位、置信度和解释文本。
4. 当意图为 `send_message` 且置信度达到阈值（建议 0.7）时，调用现有“准备发送消息”逻辑，显示确认框。
5. 置信度不足时，返回澄清问题，不直接执行。

### 联调案例

| 输入组合 | 预期结果 |
| --- | --- |
| 注视张三 0.8 秒 + 模拟语音“给他发消息，晚点开会” | 显示向张三发送的确认框 |
| 注视不足 0.3 秒 + 同一语音 | 提示请选择联系人 |
| 注视张三 + “给他发消息” | 提示补充消息内容 |
| 语音“确认发送” | 发送当前消息并清空确认区 |
| 语音“取消发送” | 取消并清空确认区 |

## 第 5 阶段：本地个性化与隐私（第 5 天）

### 要做什么

1. 继续使用本地 `profiles_demo.json` 和运行状态保存偏好。
2. 音乐模块只记录：模式、音乐类型、喜欢/跳过、时间；不记录原始音频或摄像头数据。
3. 日程模块只处理用户明确授权的文件副本。
4. 为每次多模态理解结果写一条最小审计记录：使用了哪些模态、是否成功、总耗时；不记录人脸图像。

### 用于比赛文档的表述

“系统在端侧保留短时事件窗口，仅持久化经结构化处理后的注视目标、置信度和偏好统计；不保存原始视频、音频及人脸图像，降低隐私泄露风险。”

## 第 6 阶段：测试、性能与说明（第 6～7 天）

### 最低测试要求

1. 手动跑完上表 5 个联调案例，每个至少 3 次。
2. 记录从点击“提交模拟语音”到出现确认框的耗时；目标先定为小于 1 秒。
3. 测试摄像头不可用、未注视、低置信度、空文本、连续确认等异常情况。
4. 将测试结果补充到 `tests/scenarios.json` 或新建测试说明。

### 你要提供给队友和答辩的材料

- 一张“事件接收 → 时间对齐 → 多模态信息合并 → 意图结果 → 确认执行”的流程图；
- 规则表、阈值取值和理由；
- 成功、失败和澄清案例各至少一个；
- 本地处理与隐私保护说明；
- 已知限制：第一版摄像头注视估计受光照、角度和屏幕位置影响。

1. 开工前 10 分钟：确认当天要用的 API 名称、JSON 字段和完成标准。

## 你不需要负责的内容

这些由成员 A 负责；你负责让其最终输出成为可靠、可解释的系统输入。
