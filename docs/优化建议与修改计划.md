## 赛题五原文要点

题目：**智能终端多模态输入感知与识别及个性化应答**（出自 `参考资料/2026年中国研究生人工智能大赛--华为赛题.docx`）

1. **题目描述**：面向手机/AI PC/智能音箱/车载助手等终端，用户通过语音+手势+面部表情+环境上下文等组合表达意图（如一边看联系人一边说“给他发消息”）。核心挑战：① 模态异步与时间对齐；② 多模态冲突与歧义消解（嘴上说“不要”但点头）；③ 个性化应答（结合历史习惯、偏好、上下文）；④ 端侧资源受限（模型轻量化、高实时高精度）；⑤ 隐私保护（端侧闭环、不上传云端）。
2. **系统功能要求**：
   - 多模态输入感知与对齐：至少两种模态（语音+视觉/语音+文本/语音+手势），时间维度对齐融合；
   - 意图理解与场景建模：结合当前界面、历史对话识别意图（消息发送/音乐播放/日程查询等）；
   - 个性化应答生成：基于用户画像（常用应用、使用习惯、偏好设置）生成文本/语音/图形界面反馈；
   - 部署与性能：端侧部署；推理大模型可放服务器或调公开 API，参数量 **≤14B**，允许额外 **3 个 3B 小模型**做数据处理；**单轮对话响应延时 <5s**。
3. **文档要求**：方案设计文档（多模态对齐、意图理解、个性化应答的设计原理、模型选型依据、技术合理性）。
4. **数据与训练策略**：公开数据集（CMU-MOSEI、IEMOCAP、中文多模态对话数据集等）；允许 ≤500 条人工标注（需注明来源与标注策略）；鼓励合成数据、迁移学习、自监督。
5. **提交与评分**：竞赛得分 50%（公开测试集自动评测）+ 专家评分 50%（新颖性、合理性、端侧部署可行性 + 华为内部多模态数据集泛化性）。提交：方案代码（推理脚本、模型权重或结构说明、端侧运行）、使用说明文件、可解释性文档、公开测试集结果报告。

**本项目对齐情况**：语音+视线（视觉）+屏幕上下文+手势（≥2 模态✅）；时间窗口对齐与显式取消优先冲突规则（✅）；消息/音乐/日程三场景建模（✅）；画像驱动的个性化应答（建议面板、音乐偏好、提醒建议、手势自适应画像，✅）；端侧本地运行 + qwen2.5:3b（3.09B ≤14B，✅）；单轮 <5s（LLM 2.8s 超时兜底，✅）；原始音视频/备忘录不上传（✅）。

## 一、项目现状摘要

- **架构**：`app.py`（Python 标准库 HTTP 服务，无第三方依赖）+ `web/`（纯前端，MediaPipe 本地视觉）+ `llm_reasoner.py`（可选 Ollama qwen2.5:3b 解释器）。数据落在 `data/runtime_state.json`（多用户画像分离）。
- **三大场景已基本闭环**：A 语音+视线发消息（时间窗对齐、冲突安全规则）、B 三模式音乐偏好（点头/摇头/手势反馈 + 每 3 次穿插大众常听）、C 授权备忘录日程（授权/撤销、完成状态、时间排序）。
- **已有质量底子**：前后端双重事件校验、10 秒短时事件缓存、可解释 history、撤销栈、LLM 不可用时规则兜底、`.gitignore` 排除运行状态与授权副本。
- **测试**：`tests/test_multimodal.py` 11 条单元测试（但未跑 `tests/scenarios.json` 的 30 条验收样例，见 §3-新增-1）。

### 🔴 高 —— 演示可用性 / 评委一眼可见的坏点

#### 2. 演示基准日期三方不一致（未修复，当前最致命）
- **证据**：
  - `app.py:890` bootstrap 下发 `"demo_reference_date": "2026-08-23"`，但前端从未使用（`web/app.js` 0 引用）；
  - `app.py:1250` `query_tomorrow` 硬编码 `tomorrow = "2026-08-24"`；
  - `app.py:804-809` `is_past_event` 用真实 `datetime.now()`；`app.py:840-847` `understand_schedule_query` 也用真实 now；
  - 数据：`memo_demo.json` = 08-24×3 + 08-25×1（与基准 08-23 一致）；但**当前已授权的 TXT 副本**（`authorized_memos/19ab…_备忘录演示.txt` = 08-25×3+08-26×1、`bbc…_备忘录演示1.txt` = 08-26×1）与基准不一致；
  - `runtime_state.json` 提醒时间 `2026-08-24 09:10` 与 TXT 授权内容也对不上。
- **后果**：真实系统日期已到 08-2x：① 已授权 TXT（08-25/08-26）被 `is_past_event` 标灰成“已过时间”，演示看起来全是灰色；② 硬编码“明天=08-24”在授权 TXT 里查不到任何事项 → “查询返回空”；③ 语音“明天有什么安排”与页面“查看日程”口径不一致。
- **修改意见**：
  1. `app.py` 顶部定义唯一常量 `DEMO_REFERENCE_DATE = "2026-08-23"` 及 `demo_today()` / `demo_now()` 辅助函数；
  2. `is_past_event`、`understand_schedule_query`、`query_tomorrow` 全部改用 demo 日期（推荐：`demo_now = date(2026-08-23) + 真实当前时刻`，可展示“已过时间”功能又不依赖机器日期）；
  3. 把 `备忘录演示.txt`/`备忘录演示1.txt` 日期对齐到 08-24/08-25（与 `memo_demo.json`、README 场景 C、`scenarios.json` C01 的“明天=08-24 三项”一致），并同步更新已授权副本（或让用户重新授权）；
  4. 前端在日程页显示“演示基准日期 2026-08-23”，避免演示者与评委误读“今天”；
  5. 同步 `docs/data_schema.md`、README 中的日期表述，删除各处的硬编码字符串。

#### 4. 提醒链路完全没接线（README 场景 C 的收尾缺失）
- **证据**：`app.py:1291-1296` `create_reminder` 每次追加硬编码 `{"memo_id":"memo_001","time":"2026-08-24 09:10"}` 且不去重（`runtime_state.json:17-30` 已有 3 条相同）；`decline_reminder`（`:1298`）只返回一句话；前端对这两个 action **零调用**；`query_tomorrow` 返回的 `suggestion` 字段前端也不渲染。
- **修改意见**：
  1. 后端：`create_reminder` 改为按事项推导提醒时间（如 memo_001 的 10:00 减去画像 `schedule_reminder_minutes=50` → 09:10），校验 memo 存在，按 `(memo_id, time)` 去重；`decline_reminder` 记录一条 history；
  2. `schedule_query_result` 增加 `reminder_offer` 字段（首个高优先级未过期事项的建议提醒时间）；
  3. 前端日程页在查询结果下渲染“需要我在 09:10 提醒你参加「组会」吗？［提醒我］［不要］”，调用 create_reminder / decline_reminder，并把提醒写入历史与撤销栈；
  4. 在“本地交互历史”中展示最近提醒。

#### 12. 建议面板“查询今天安排”按钮行为与文案不符
- **证据**：`web/app.js:2056` `query_today` 与 `query_schedule` 走同一个 `api('query_schedule')`（全部日程），并非“今天”。
- **修改意见**：给 `query_schedule` 加可选 `date`/`scope` 参数（today/tomorrow/all），`query_today` 调 `{scope:'today'}`；与 §高-2 的 demo 日期联动。

#### 13. 导航离开音乐页会静默停模式、切回又自动开“热门推荐”
- **证据**：`web/app.js:2086` 切到非音乐页 `await stopMode()`；`:2093` 切回音乐页自动 `activateGeneralMusic()`。README 场景 B 语义是“用户停止或确认切换才结束模式”，导航不应打断；且自动开启 general 会覆盖当前播放曲目。
- **修改意见**：导航不停止模式（仅显式“停止模式”/切换画像/刷新页面时结束）；切回音乐页若已有模式则恢复原模式视图而非强制 general。

### 🔴 高 —— 个性化亮点链路失效（赛题“个性化”得分点）

#### 3. 头部手势自适应画像数据链路断裂（未修复）
- **证据**：`web/app.js:937-1013` `observeHeadGesture` 已算出 `horizontalRange/verticalRange/directionalYaw/directionalPitch`（`:961-970`），但 `recordHeadDecision`（`:555-562`）payload 只有 `{page,decision,gesture,purpose}`；`likeCurrentTrack`（`:1742`）/`dislikeCurrentTrack`（`:1789`）也未传幅度；后端 `app.py:237-245` `update_gesture_profile` 需要 `payload.motion_strength∈(0,1)`，`undo_last_nontext_operation`（`:303-309`）需要 `motion_strength`。结果：`gesture_profile.confirmed_samples` 恒空、`head_min_strength` 恒 0（`runtime_state.json:208-212` 实证）。
- **修改意见**：
  1. 在 `observeHeadGesture` 识别出点头/摇头时，把幅度归一化为 `motion_strength`（如 `min(0.9, max(horizontalRange, verticalRange)*k)` 夹到 (0,1)），追加到 `recordHeadDecision` 的 payload；
  2. `like/dislike` 分支把 `motion_strength` 透传给 `api('like_track'/'dislike_track')`，后端 `push_undo` 的 `motion_strength` 才有值；
  3. `update_gesture_profile` 兼容 `payload.vertical_range/horizontal_range`（或只用 motion_strength，二选一保持单一来源）；
  4. 在“本地交互历史与撤销”面板展示画像：`已学习 N 次动作幅度 · 最小触发阈值 0.xx`，让“自适应”可见可讲。

#### 5. 建议面板“基于历史的高频操作”基本死链（未修复）
- **证据**：`app.py:317-332` 目录 ID（`focus_contacts/prepare_message/start_focus/resume_music/query_schedule/query_today`）与真实历史 action（`open_page/select_contact/like_track/toggle_playback/undo/…`）几乎零交集，回退逻辑（`:349-354`）恒定落到 `allowed_actions[:2]`；且 `open_page`（`:969`）每次切页都写一条历史，进一步稀释信号。
- **修改意见**：
  1. 目录项增加 `match_actions` 映射（如 `prepare_message ← select_contact/send_message/confirm/cancel`、`resume_music ← like_track/dislike_track/next_track/toggle_playback/complete_track`、`query_schedule ← query_schedule/toggle_event_completion/authorize_memo`）；
  2. 回退时按 `match_actions` 计数，并把 `open_page`/`undo` 从 `frequent_actions` 排除（或 `open_page` 不写历史）；
  3. `suggest_local_actions` 的 LLM 输入同步改为映射后的高频操作名，让模型推荐更有依据。

### 🟡 中 —— 健壮性与一致性

#### 6. 并发写状态无锁（未修复）
- **证据**：`ThreadingHTTPServer` + 每个请求独立 `load_state()`→改→`save_state()`（整文件重写）；无全局锁。多个请求（`sendBeacon`、切页 `screen_context`、手势事件）并发会 last-writer-wins 丢更新；另外 `do_POST`（`app.py:905`）在返回时又 `load_state()` 一次——每个摄像头事件都白读一遍整文件。
- **修改意见**：
  1. 模块级 `STATE_LOCK = Lock()`，`handle_action` 整体包在锁内（load→mutate→save 原子化）；demo 规模足够；
  2. `save_state` 改原子写（临时文件 + `os.replace`），避免写一半被读；
  3. `do_POST` 直接返回本次 handle_action 使用的 state（不再二次 load），`record_multimodal_event` 类轻量请求可省略响应里的 state。

#### 7. interaction_history 空 metrics 守卫（部分修复收尾）
- **修改意见**：`append_interaction_history` 在白名单过滤后为空时**不写** `metrics` 字段（当前会写 `metrics:{}`）；配合 §高-3 前端真正传入幅度后，白名单才有实际作用。

#### 8. 清理遗留字段 preference_adjustments（未修复）
- **证据**：`runtime_state.json` 顶层 `:32-48` 与 `profile_states` 内仍存在；`app.py:32-37` `PROFILE_STATE_FIELDS` 仍包含；`load_state` 只做兼容迁移不删除。
- **修改意见**：从 `PROFILE_STATE_FIELDS`、`default_state`、`profile_runtime_defaults` 移除；`load_state` 加载后 `state.pop("preference_adjustments", None)`（track_preferences 已是事实标准）；顺带清理 `profile_states` 内的旧字段。

### 🟢 低 —— 评测、测试与文档
