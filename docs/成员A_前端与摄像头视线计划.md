# 成员 A 计划：前端交互、摄像头视线与语音模拟

## 你的目标

负责让用户能“看见、操作、理解”系统。你的阶段性成果是：用户打开联系人页面、允许摄像头、注视联系人卡片并输入模拟语音后，页面把三种信息显示出来并交给后端处理。

第一版的模态组合为：

- 摄像头：真实摄像头画面 + 人脸关键点 + 注视方向估计；
- 语音：**模拟语音文本**，例如点击预设语句或在输入框输入“给他发消息，晚点开会”；
- 屏幕上下文：当前页面、当前可见联系人卡片和用户选中的卡片。

> 重要边界：摄像头图像只在本机浏览器内处理，不上传、不保存录像。首次打开摄像头前必须显示授权提示和“关闭摄像头”按钮。

## 开始前准备（第 0 天，约 1 小时）

1. 从 GitHub 克隆项目，或在已有项目文件夹中执行 `git pull`。
2. 在 VS Code 安装扩展：Python、Live Share（两人协作时使用即可）。
3. 阅读以下文件，先理解当前演示怎样工作：
   - `web/index.html`：页面结构；
   - `web/app.js`：按钮事件和请求；
   - `web/styles.css`：页面样式；
   - `README.md`：启动方式。
4. 启动项目后，在浏览器确认消息、音乐、日程三个模块可访问。
5. 新建自己的分支，例如：`feature/webcam-gaze`。不要直接在 `main` 上开发。

## 第 1 阶段：摄像头授权与预览（第 1 天）

### 要做什么

在网页右上方增加一个全局“开启摄像头 / 关闭摄像头”控制区，并在右上角显示小型视频预览。一次授权后，消息、音乐和日程三个模块都可使用同一条本机摄像头流。

### 实现要点

1. 在 `web/index.html` 增加 `<video>` 元素；它要有 `autoplay`、`muted`、`playsinline` 属性。
2. 在 `web/app.js` 中通过浏览器 `navigator.mediaDevices.getUserMedia({ video: true, audio: false })` 获取摄像头流。
3. 将返回的 `stream` 赋给 `video.srcObject`。
4. 点击关闭时：停止 `stream.getTracks()` 中的每一条轨道，清空 `video.srcObject`。
5. 用户拒绝授权时，在页面显示清楚的中文提示，例如“未获得摄像头权限，无法启用注视识别；仍可使用手动选择联系人进行演示。”

### 完成标准

- 首次点击会弹出浏览器摄像头授权窗口；
- 授权后可以看到自己；
- 点击关闭后摄像头指示灯熄灭；
- 刷新或关闭页面后会关闭摄像头；切换业务模块时保持摄像头开启，供新的页面上下文继续使用；
- 不新增任何图片、视频或人脸数据文件。

## 第 2 阶段：人脸关键点检测（第 2～3 天）

### 为什么要分两步

摄像头画面不等于系统知道用户在看哪里。先可靠地检测到人脸、眼睛和虹膜，再做“看向哪个联系人”的判断，能更容易排错。

### 推荐技术路线

使用浏览器端的 MediaPipe Face Landmarker / Face Mesh。它可在浏览器侧取得人脸和眼部关键点，不必把视频上传服务器。实现前先查看其官方 Web 文档和示例；不要复制来源不明的模型文件。

### 要做什么

1. 在视频预览上覆盖一个 `<canvas>`。
2. 加载人脸关键点模型，在每一帧视频中检测一张人脸。
3. 在 canvas 上画出眼部和虹膜附近的关键点，作为调试可视化。
4. 增加状态文字：`未检测到人脸`、`已检测到人脸`、`请正对屏幕`。
5. 每隔约 100～200ms 做一次检测即可；不要为了每一帧都跑模型而造成页面卡顿。

### 完成标准

- 能显示“是否检测到人脸”；
- 调试模式中，眼部关键点会随脸部移动；
- 遮住摄像头或离开画面时状态正确变为“未检测到人脸”；
- 常用笔记本上页面仍能流畅点击按钮。

## 第 3 阶段：把注视方向映射到联系人（第 4～5 天）

### 第一版应达到的效果

不追求精确追踪真实眼球视线。第一版只需判断用户大致在看屏幕的左、中、右或上、中、下区域，并据此映射到联系人卡片的位置。

### 实现步骤

1. 为每个联系人卡片读取屏幕坐标：使用 `element.getBoundingClientRect()` 获取中心点。
2. 使用人脸/虹膜关键点相对眼眶的位置，计算一个归一化的 `gazeX`、`gazeY`（范围约为 0～1）。
3. 将 `gazeX`、`gazeY` 映射成页面坐标，计算与每张联系人卡片中心点的距离。
4. 最近卡片距离小于阈值，且连续注视同一张卡片至少 `800ms` 时，才判定为一次有效注视。
5. 给该卡片加蓝色高亮边框，并显示“当前注视：张三”。
6. 注视目标变动、脸丢失、距离过远时，清除候选状态。

### 必须发送的事件格式

向后端 `/api/action` 发送以下结构（字段名不要自行改动）：

```json
{
  "action": "record_multimodal_event",
  "event": {
    "modality": "gaze",
    "timestamp_ms": 1720000000000,
    "confidence": 0.78,
    "payload": {
      "target_type": "contact",
      "target_id": "contact_zhangsan",
      "dwell_ms": 820
    }
  }
}
```

`timestamp_ms` 使用 `Date.now()`；`confidence` 可以先按脸部检测质量和停留时间给一个 0～1 的估计值。

### 完成标准

- 注视张三卡片约 0.8 秒后显示高亮；
- 短暂扫过其他卡片不会频繁切换；
- 事件会出现在浏览器调试面板或控制台；
- 摄像头无法使用时，仍保留“点击联系人卡片”作为演示备用路径，并明确显示它是备用输入。

## 第 4 阶段：模拟语音输入与上下文记录（第 6 天）

### 要做什么

1. 在联系人场景放置输入框和三个预设按钮：
   - `给他发消息，晚点开会`；
   - `确认发送`；
   - `取消发送`。
2. 用户点击“提交模拟语音”时，生成 `speech_text` 事件。
3. 同时生成 `screen_context` 事件，至少包含当前页面 `contacts` 和当前可见联系人 ID 列表。
4. 将这三类事件提交给后端的“对齐与理解”接口。

示例语音事件：

```json
{
  "modality": "speech_text",
  "timestamp_ms": 1720000001200,
  "confidence": 1.0,
  "payload": { "text": "给他发消息，晚点开会" }
}
```

## 第 5 阶段：联调与演示（第 7 天）

与成员 B 一起走通 10 次场景 A，并记录每次是否正确解析为张三。

检查清单：

- 摄像头关闭时，页面不会报错；
- 只看张三、不提交语音时，不能自动发消息；
- 只说“给他发消息”但没有有效注视时，系统要求用户选择联系人；
- 有有效注视 + 模拟语音时，系统显示待发送给张三的确认框；
- 确认或取消后，确认框与消息内容均清空；
- 不保存视频、人脸图像或原始关键点历史。

## 遇到问题时如何判断

| 现象 | 优先检查 |
| --- | --- |
| 看不到画面 | 浏览器摄像头权限、是否被其他软件占用、是否用了 HTTPS/localhost |
| 检测不到人脸 | 光照、摄像头角度、模型是否加载成功、canvas 尺寸是否与视频一致 |
| 注视目标总是错 | 先检查卡片坐标和 `gazeX/gazeY` 的调试显示，再调整阈值 |
| 页面很卡 | 降低检测频率和视频分辨率，先确保 5～10 FPS 的稳定识别 |
| 后端不识别事件 | 对照本文的 JSON 字段名、时间戳单位是否为毫秒 |

## 你不需要负责的内容

- 意图分类与“他”指代消解规则；
- 多模态事件的服务端缓存和时间窗口；
- 个性化偏好计算与日程解析。

这些由成员 B 负责，但你们必须共同确认事件格式。
